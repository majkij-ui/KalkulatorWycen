# Plan: KSeF as the source of invoices (K-track)

> Source: M.J., 2026-10-30. Sales invoices from KSeF become the truth about invoices in the hub from
> 01.01.2027; purchase invoices become a source of gear and cost information. 2026 data stays as it is.

## 1. Stages

| Stage | What | Status |
|---|---|---|
| K0 | Read-only client, proof on the Ministry's TEST environment | done 2026-10-30 |
| K1 | M.J.'s own token in the macOS Keychain; preview from the real account, nothing written to the hub | waits for the final token rules (§3) |
| K2 | Sales: `npm run data -- ksef-sync` writes proposals to Skrzynka, calendar events, overwrite rules (§5) | waits for K1 and M.J.'s approval of §5 |
| K3 | „Zakupy" tab in Sprzęt: new gear, small items (`onSet: false`), other cost | waits for K1 |

## 2. Safety model

1. **Token with `InvoiceRead` only**, generated by M.J. and stored in the Keychain, never in the repo, a file or chat.
2. **`lib/ksef-client.ts` has an endpoint allowlist.** Anything outside it throws before a request is made.
3. **The client refuses a wider token.** It reads the `per` field of the access token and accepts only
   `["InvoiceRead"]`; an unreadable field also means refusal.
4. **The hub changes only through Skrzynka proposals**, with the existing backups and `--dry-run`.
5. `scripts/ksef-test-env.mts` is the only code that issues invoices. Its address is fixed to TEST, with no
   switch to production.

## 3. Open before K1

- **Token rules.** Binding today: tokens work until 31.12.2026. Draft of 27.10.2026 (consultation until about
  10.11, known from a blog summary, not read in the original): tokens generated from 2027 valid up to 365 days,
  older ones until 30.11.2027. Check the published regulation in December. If tokens end, K1 needs a KSeF
  certificate, so only `authenticate()` in the client should change.
- **`per` on production.** Seen on TEST only. If production differs, the client refuses to work rather than
  working unguarded; K1 will show it.

## 4. Results of K0 (`npm run ksef:test`, TEST, 2026-10-30)

| Check | Result |
|---|---|
| Login with a read-only token; seller sees the sale, buyer sees the purchase | OK |
| XML gives the due date and lines (metadata has neither) | OK |
| Read-only token opens an invoice-issuing session | refused, HTTP 403 |
| Read-only token creates a token with `InvoiceWrite` | refused, HTTP 400, code 26001 |
| Read-only token grants permissions to someone else | refused, HTTP 403 |
| Client given a token with `InvoiceWrite` | refuses to work |
| **Read-only token creates another read-only token** | **allowed, HTTP 202** |

The last row matters after a leak: revoking the one known token may not be enough. List all tokens in the
Ministry's app and revoke every unknown one. Whether revoking a token also revokes those it created was not tested.

## 5. Proposed rules for K2 and K3 (not yet approved by M.J.)

| Case | Behaviour |
|---|---|
| Invoice matches one open project of the client | Proposal to overwrite number, amount and due date; old data in the backup |
| Client has several open projects | M.J. picks the project, nothing automatic |
| No matching project | „Nieprzypisane"; revenue does not change by itself |
| Issued 31.12, KSeF number 02.01 | Calendar 02.01 (reaches the client); revenue in the year of issue |
| Correction invoice | Changes the original's amount and shows both documents; no new revenue |
| Invoice in EUR | To decide in K2: invoice amounts in EUR are not modelled in the hub today |
| Payment | Unchanged, `invoice_paid` stays in the hub; KSeF does not know about payments |
| Purchase with several lines | Each line categorised separately; gear gets the net amount |
| Correction or return of gear | Warning and a proposal to change the price |

Limits: not in KSeF are receipts and, as a rule, invoices from foreign sellers (Adobe, Google), so costs stay
partly manual. KSeF allows 20 exports an hour; K2 syncs on demand and uses the metadata query.
