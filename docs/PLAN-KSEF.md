# Plan: KSeF as the source of invoices (K-track)

> Source: M.J., 2026-10-30 and 2026-11-13. Sales invoices from KSeF are the truth about invoices in the hub from
> 01.02.2026 (when M.J. started issuing in KSeF); purchase invoices become a source of gear and cost information.

## 0. The hub never adds invoices to KSeF

Decision of M.J., 2026-10-30: invoices are issued in the panel provided by the accounting firm. The hub only reads.
A test in `lib/ksef-reconcile.test.ts` fails if any app or script code outside `scripts/ksef-test-env.mts` touches
the invoice-sending endpoints or asks for `InvoiceWrite`. That script issues fake invoices on the Ministry's TEST
environment only, because the read-only client needs something to read; nothing in the app imports it.

## 2. Safety model

1. **Token with `InvoiceRead` only**, generated by M.J. and stored in the Keychain, never in the repo, a file or chat.
2. **`lib/ksef-client.ts` has an endpoint allowlist.** Anything outside it throws before a request is made.
3. **The client refuses a wider token.** It reads the `per` field of the access token and accepts only
   `["InvoiceRead"]`; an unreadable field also means refusal.
4. **The hub changes only through Skrzynka proposals**, with the existing backups and `--dry-run`.
5. `scripts/ksef-test-env.mts` is the only code that issues invoices. Its address is fixed to TEST, with no
   switch to production.

## 3. Open before K1

- **Token rules.** Binding today: tokens work until 31.12.2026. Draft of 27.10.2026 (consultation until about
  10.11, known from a blog summary, not read in the original): tokens generated from 2027 valid up to 365 days,
  older ones until 30.11.2027. Check the published regulation in December. If tokens end, K1 needs a KSeF
  certificate, so only `authenticate()` in the client should change.
- **`per` on production.** Seen on TEST only. If production differs, the client refuses to work rather than
  working unguarded; K1 will show it.

## 4. Results of K0 (`npm run ksef:test`, TEST, 2026-10-30)

| Check | Result |
|---|---|
| Login with a read-only token; seller sees the sale, buyer sees the purchase | OK |
| XML gives the due date and lines (metadata has neither) | OK |
| Read-only token opens an invoice-issuing session | refused, HTTP 403 |
| Read-only token creates a token with `InvoiceWrite` | refused, HTTP 400, code 26001 |
| Read-only token grants permissions to someone else | refused, HTTP 403 |
| Client given a token with `InvoiceWrite` | refuses to work |
| **Read-only token creates another read-only token** | **allowed, HTTP 202** |

The last row matters after a leak: revoking the one known token may not be enough. List all tokens in the
Ministry's app and revoke every unknown one. Whether revoking a token also revokes those it created was not tested.

## 5. Rules (approved by M.J. 2026-10-30, revised 2026-11-13)

| Case | Behaviour |
|---|---|
| Value of a project in the hub | Price from Finanse projektu (PDF → frozen at acceptance → typed by hand) + extra sales. Realizacja never changes it. Invoices win once they cover it or the project is done |
| Invoice and project | Matched by number, then by client and the amount still uninvoiced, then by the only project of that client; amount alone is only a suggestion to confirm |
| One project, two invoices (main job + extra sale) | One project with two invoices; their sum is set against price + extra sales |
| Invoice amount differs from the hub | Shown as „Różnica kwoty"; applying writes the invoice, the price stays for M.J. to correct |
| Invoice in EUR | No amount in the zł field; the EUR amount is kept beside it |
| Correction | Attached to its invoice; the amount after corrections is the invoice amount |
| Project without an invoice in KSeF | „Brak faktury", or „Bez faktury (celowo)" for a barter; a project still in progress is just waiting |
| Project settled before KSeF (January 2026) | Left out |
| Dates | Calendar = the day KSeF gave the number; revenue month = issue date |
| Client names | Project field `client` = display name. `client-details.json` keeps the name on the invoice and the NIP; one NIP = one display name, so later invoices of that firm land on the same client |
| Overwriting | Only on „Zastosuj"; the old values stay in the event's `updatedFrom[].before` |

## 7. „Zgodność z KSeF" (built 2026-11-13)

- `npm run data -- ksef-sync` writes `ksef/sprzedaz.json` in the hub data folder (a new file swapped in whole, so
  it runs with the hub open). Already downloaded invoices are kept, so a run downloads only new ones.
- The app reads it in Finanse → „Zgodność z KSeF" (`lib/ksef-reconcile.ts`, `components/finance/ksef-panel.tsx`):
  one card per project with the hub value, the KSeF invoices, the difference, the changes and „Zastosuj z KSeF";
  „Zastosuj wszystkie pewne" applies confident rows without an amount difference; invoices without a project get a
  project picker; a project without an invoice can be marked „Bez faktury". Decisions: `ksef-decisions.json`.
- Klienci shows the invoice name and NIP under the display name; „Scal nazwy" carries them to the new name.
- KSeF limits met on the real account: metadata 20 an hour, downloads 16 a minute and 64 an hour.
- Later: bank CSV as a fourth column („Wpłynęło"), purchases tab in Sprzęt, VAT tracking.

## 8. Second pass after M.J.'s first look (2026-11-13)

M.J.'s brief: the hub's data should be verified by KSeF, and when the two drift apart the app should help him
through it with sensible suggestions; a close invoice always exists somewhere, and when it doesn't, that is his
signal that something needs attention.

- Tab renamed „KSeF", with two views: „Zgodność z projektami" and „Faktury".
- **Everything is correctable by hand** (decisions in `ksef-decisions.json`): move an invoice to another project or
  detach it; say which hub entry it replaces, or that it is a further invoice of the project (`pair`); an invoice
  already saved in one project moves with its entry instead of being duplicated; a hub invoice that is not in KSeF
  can be removed from the card.
- **Suggestions with reasons**: a project without an invoice (or under-invoiced) lists unassigned invoices that fit
  (same client, amount equal or within 15 %, date within 60 days); an unassigned invoice lists the best projects
  the same way. A finished project with no candidate says so plainly.
- **Amount difference** offers, most specific first: remove the extra sale that is not on the invoice (sum or single
  item equals the difference), adjust the only extra sale by the difference, add the difference as an extra sale
  (invoice higher), accept the KSeF amount, or „waits for a correction". An accepted difference holds only for that
  amount; a new invoice or correction reopens it.
- **„Faktury"**: sales and purchases with period totals (count, net, VAT, gross; other currencies beside), search,
  and a detail dialog with the lines. KSeF stores invoices as XML, not PDF, so there is no PDF to open.
- `ksef-sync` now also copies purchases (`ksef/zakupy.json`) and is incremental: after the first run it asks only
  for invoices stored since the previous one. Invoice content downloads sales first, 55 a run; invoices still
  waiting are listed with amounts and dates and stay out of the reconciliation.
- With no copy yet, the screen shows only how to fetch it (before: every project looked like „Brak faktury").

## 9. „Pobierz z KSeF” in the app (2026-11-14)

M.J.: a button in the app should fetch new invoices, not a terminal command.

- Finanse → KSeF has „Pobierz z KSeF”. It runs the same synchronisation as `npm run data -- ksef-sync`
  (`lib/ksef-sync.ts`, shared by both), shows progress, then a plain summary: how many new invoices, and what is
  left for the next run when KSeF's hourly limit stops it.
- The window has no network access of its own. Requests go through two commands in `src-tauri/src/ksef.rs`:
  `ksef_request` builds the address from the environment name and repeats the read-only allowlist in Rust;
  `ksef_token` reads the token from the Keychain through the system `security` tool (no macOS prompt, because
  that tool created the entry). The token is used only to log in and is never written anywhere.
- `lib/ksef-client.ts` encrypts with WebCrypto (key taken from the certificate by a small DER reader), so the same
  code runs in Node and in the window.
- NIP: company settings, else the NIP of the existing copy, else the screen asks for it.
- No token in the Keychain: the screen shows the one terminal command that saves it. Saving the token from inside
  the app is not built.
- Proven: Rust tests (allowlist; on request, a live call to KSeF's public certificates and a Keychain read),
  `ksef-sync --dry-run` on the real account with the new encryption, unit tests of the sync, the bridge and the
  texts. The button itself needs a built app to try.

## 10. Bank statement, payments and taxes (2026-11-14)

M.J.: KSeF plus the bank CSV are the final truth (edge cases aside, like the one barter). He wants to load the
bank file, see which invoices are paid, have projects show the same, and see ZUS, flat tax and VAT actually paid.

Decided with M.J.:

| Case | Behaviour |
|---|---|
| Transfers from private persons for „sesje" (another activity on the same NIP) | Outside the hub. They sit in „Wpłaty bez faktury", where a sender can be ignored for good |
| Purchases | Not checked against the bank for now (they are paid from another account); from 2027 |
| PIT-38, VAT-9M, transfers to own accounts, loan overpayment | Outside the hub (`outside`) |
| VAT payer | From June 2026 (`VAT_PAYER_SINCE`) |
| „What did VAT give me" | Two numbers side by side: sales VAT − paid to the tax office (real), and deductible VAT by KSeF purchase invoices |
| Fuel | Half of the VAT is deductible; recognised by invoice lines, whatever the station |
| Purchase invoice that is not the firm's | Marked by hand in KSeF → Faktury → Zakupy (0 %) |
| Payment → project | As with KSeF: nothing changes by itself, „Zastosuj wszystkie pewne" writes confident matches |
| Flat tax | Paid (bank) next to the hub's estimate; the profit calculation is untouched |
| ZUS for September–November 2026 | Paid from ERSTE, no file: entries carry `paidFrom` and are not looked for in the statement |

Built:

- `lib/bank-statement.ts`: mBank „Lista operacji" CSV → operations with a kind (`income`, `internal`, `tax_vat`,
  `tax_flat`, `zus`, `fee`, `outside`) and a stable id, so files with overlapping periods do not duplicate. Copy in
  `bank/operacje.json` (not in the automatic backups: it can be rebuilt from the files).
- `lib/bank-match.ts`: incoming transfers against KSeF sales invoices, gross, in the invoice currency: manual
  decision → invoice number in the title → same payer and amount → one transfer for several invoices → amount
  alone (a suggestion to confirm). `paymentChanges` turns confident, fully paid invoices into `invoice_paid`
  entries (bank day, net amount, invoice number, operation ids); a manual entry is corrected and keeps its old
  values in `updatedFrom` (type `bank`).
- `lib/taxes.ts`: a transfer to the tax office in month M settles M−1; ZUS is compared within the transfer month,
  as the hub stores it. A month without a statement is „unknown", never „unpaid".
- Finanse → KSeF: „Wczytaj wyciąg z banku", a payment mark on every invoice (paid with the day, partial, waiting,
  overdue, no statement), payments to write on the project card, „Wpłaty bez faktury w KSeF" grouped by sender.
  Decisions live in `ksef-decisions.json` (`bank_assign`, `bank_ignore`, `bank_sender`, `purchase_vat`).
- Finanse → „Podatki": monthly ZUS, flat tax and VAT, and the VAT comparison.
- Koszty stałe: ZUS gets a „bank" mark when the statement has a transfer of that amount in that month; another
  amount offers „popraw", a missing transfer can be marked as paid from another account, and a transfer without
  a hub entry offers to add it.

Checked read-only on M.J.'s real file for 2026: every sales invoice past its term is matched to a transfer, ZUS in
the statement equals the hub's entries to the grosz, and several payment days in projects differ from the bank.
The two VAT numbers differ; fuel and the invoices his accountant does not book explain part of it, VAT on sales
outside KSeF most of the rest.

**Sessions and VAT (M.J., 2026-11-14, later the same day):** the sessions were sold with VAT, and the transfer is
123 % of the price. Transfers from senders marked „Pomijaj tego nadawcę" are therefore treated as sales outside
KSeF: still not revenue of the hub, but their VAT (transfer × 23/123, only from June 2026) is added to the sales
VAT in „Podatki", and a note there says how much came in. With it the two VAT numbers agree to within the
rounding of a few declarations and purchases that never reach KSeF.
